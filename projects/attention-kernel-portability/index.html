Overview

If you pick the fastest attention backend on one GPU, is it still the fastest on another GPU, and what does it cost if it is not? I measured this for forward prefill and single-token KV-cache decode on six NVIDIA GPUs covering Ampere, Ada, Hopper and Blackwell, all under one software build.

Most configurations did not have a clearly fastest backend. Only 128 of 447 prefill and 409 of 1203 decode configurations had a winner that was at least 10% ahead of second place and statistically separated from it. Among those, the winner changed between GPUs in 27 of 64 prefill comparisons but only 29 of 289 decode comparisons. Across all GPU pairs, reusing the source GPU’s choice usually cost almost nothing (median 1.002x prefill, 1.000x decode). The tail was worse, at 1.61x for prefill and 1.32x for decode at the 95th percentile.

Experimental setup

Prefill covers batch 1, 4, 16 and sequence lengths 256, 512, 1,024, 2,048, 4,096, 8,192. Decode appends one token to a KV cache of length 512, 1,024, 2,048, 4,096, 8,192, 16,384 at batch 1, 8, 32, 64. The full grid also varies dtype (bf16 and fp16), head dimension (64 and 128), causal masking and, for decode, eager execution against CUDA Graphs. The figures below show a bf16, head dimension 128 slice. I measured 16 implementation variants from seven backend families.

Decode

Decode does little arithmetic and reads the whole KV cache, so I report it in bytes. The KV footprint for one decode step is

bytes  =  2 B Hkv N D s\text{bytes} \;=\; 2 \, B \, H_{kv} \, N \, D \, sbytes=2BHkv​NDs

where BBB is batch, HkvH_{kv}Hkv​ the number of KV heads, NNN the KV length, DDD the head dimension and sss the bytes per element. The factor 2 counts K and V. Effective bandwidth is this byte count divided by measured time. It is a model and was not read from a profiler.

Decode was measured with and without CUDA Graphs. The figures use eager execution, and every comparison uses the same mode on both GPUs.

Fewer KV heads did not speed up every backend. At batch 1, N=16,384 on H100, going from 32 to 8 KV heads cuts the cache from 268 MB to 67 MB. FlashAttention improves from 129.5 to 103.8 us, SDPA stays about the same (135.9 to 142.3 us), and FlashInfer gets slower (280.3 to 859.7 us).

Limitations

  • Each GPU was measured on a different host, so hardware effects are mixed with host effects.
  • The dispatch probe covered 66.5% of timed runs. For the rest, I cannot confirm which kernel actually ran.
  • No profiler counters were collected, so bandwidth numbers come from the byte model.
  • FlashInfer page size equals the KV length in every decode run, so the FlashInfer and FlashAttention comparison is between libraries and says nothing about paged against contiguous layouts.
  • Results hold for torch 2.9.0+cu128, CUDA 12.8, Triton 3.5.0, flash-attn 2.8.3 and FlashInfer 0.6.18. Other versions may rank differently.

Run outcomes

Every attempt ends in one of five states. OK is a clean timed run. UNSUPPORTED means the library rejected the configuration. OOM_PREDICTED means the run was skipped because it would not fit in memory. OOM means it ran out of memory anyway. ERROR means it crashed at run time, and all 950 of these are FlashInfer on the RTX 5090.

Dispatch checks

For each run I recorded which kernel actually executed. Among probed runs, 0.449% ran a different kernel than the one requested. 33.5% of runs were not probed, mostly on the library paths. P4-fa2 has 3,067 unprobed runs and 932 confirmed as flash-attn.

TorchInductor’s attention-fusion counter read zero in all 3,645 runs where it was recorded, yet 45 profiled Inductor runs executed a flash-attention kernel. The counter alone is not a reliable signal of what ran.

Correctness

Every implementation was checked against the PyTorch reference on a sample of configurations, and none failed. Relative error is inflated where reference values are near zero, so absolute error and cosine similarity are the useful columns.

Code sources

I wrote the PyTorch reference (P0-naive, D0-naive-kv), its torch.compile variants (P1-inductor*, D1-inductor) and the SDPA call sites that force one backend each (P2b, P2c, P2d, D2-sdpa). P3-triton is the Triton tutorial kernel with a small BF16 change. P4-fa2, P4h-fa3, D3-fa-kvcache, D6-fa-prefill-at-1 and D4-flashinfer call the unmodified flash-attn 2.8.3 and FlashInfer 0.6.18 libraries.
