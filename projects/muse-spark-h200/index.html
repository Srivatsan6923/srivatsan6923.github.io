Optimizing Muse Spark inference on H200

How KV-cache access, expert weight reuse and decoder scheduling shaped kernel and serving performance

I spent the Open Kernel Challenge making Muse Spark Open, an 816-billion-parameter mixture-of-experts model, run faster on NVIDIA H200 GPUs. I wrote new kernels for attention, the expert layers and the dense projections, then carried the most useful ones into SGLang, the serving engine the challenge is built around.

The result that shaped everything after it came early. I made the projection kernels in one decoder layer faster, the profiler showed 8.7 µs less GPU-busy time, and the layer finished only 1.2 µs sooner. From then on I asked three questions of every kernel: how many bytes it moves, how often each byte is reused, and which dependency gates the next stage. The challenge's stock layer takes 172.1 µs on that shape; my final one takes 83.3 µs. On the eight-GPU server the gains were smaller: the one change the challenge scored reached 1.022×, and with all four of my changes stacked a 16-user test reached 1.283×.

Srivatsan · solo entry, October–November 2026. Every kernel and serving change here is my own design and implementation; where my code calls a library (cuBLAS and cuBLASLt, DeepGEMM, FlashAttention-3), the text says so.

Decoder layer · batch one

Where the decoder layer was waiting

One Muse Spark layer, as each GPU runs it, is a chain of about a dozen dependent kernels: the QKV projection, attention, the output projection and residual norm, and then two branches that run side by side. On the main stream the pooler projects the hidden state into the expert width. On a second stream the router scores 256 experts, a top-8 kernel picks eight of them, and a small kernel builds the per-expert routing tables. The expert GEMM needs both results before it can start.

I started by making the biggest kernels faster. The projections were among the biggest, so I rewrote them, and the profiler agreed that the GPU was busy for less time. The layer barely noticed (Figure 1).

Kernels in this layer overlap, across the two streams and through programmatic dependent launch (PDL), which lets a kernel launch before the one feeding it has finished. That makes the profiler's totals hard to read. GPU-busy time removes the overlap but still counts a kernel parked at its PDL wait, so a drop in busy time can mean shorter waits as easily as less work. Elapsed time is the only number that tells you whether the layer got faster.

My reading of the gap is that the expert GEMM had been waiting on the routing branch all along. A faster pooler simply arrived at the join earlier and waited longer (Figure 2). If that was right, the next gain had to come from the routing side, even though none of its kernels looked expensive.

So I went after the routing branch with four changes: (1) chaining its kernels with PDL so that each launches while the previous one runs, (2) moving the router's output memset to the start of the layer, where it hides under attention, (3) a top-8 kernel that handles each token in a single warp instead of reducing across warps, and (4) a retuned split of the router's K dimension. A newer attention kernel for this shape landed in the same period, so I credit the result to the set as a whole: elapsed layer time went from 90.1 to 83.3 µs.

Two earlier changes followed the same logic without making any kernel faster at all: building the routing tables off the main stream, and letting the expert GEMM start loading its weights before its PDL wait. The projection kernels and the one-launch router themselves are in the appendix. They mattered less than I first thought, which is the point of this section.

The lesson I took from this layer is that at batch one a decoder layer is a dependency graph, and the profiler's totals hide which edge is critical. Even the final version is a chain of about a dozen kernels, each boundary adding a launch, a wait and a round trip through memory. A persistent kernel that keeps the whole layer on chip is what I would build next.

Open questions
  • Which branch really arrives last: %globaltimer stamps at the end of the pooler, the routing tables and the start of the expert GEMM would settle it.
  • How much each of the four routing changes contributed on its own.
  • What one kernel boundary costs in this chain.
Attention · score 1.97× over FlashAttention-3

Reading a fragmented KV cache

The timed call covers the whole attention step SGLang runs for one layer: normalizing queries and keys, rotary embeddings on sliding-window layers, writing the new keys and values into the FP8 cache, attending over the window or the full context, and a sigmoid-gated output. Each GPU holds 16 query heads and 2 KV heads of dimension 64. Batches have 1, 16 or 32 requests with contexts drawn within ±7.5% of 80,000 tokens, and carry one new token per request in decode or eight in speculative verify. The cache uses one token per page, so consecutive tokens can sit anywhere in memory, and that one detail drives most of this section.

Full-context decode reads two 128-byte rows per cached token, one of keys and one of values. At batch 32 that is 655.36 MB at the nominal 80,000 tokens, which the H200's 4.8 TB/s could stream in 136.5 µs at best. Each byte feeds only about 16 FLOPs per query, so this is a pure gather problem: the kernel is as fast as it can pull scattered rows out of HBM.

My first kernel's attention loop managed 1.61 TB/s on batch-16 full decode (203.8 µs), about a third of the peak. I assumed the page-table lookups were the bottleneck and loaded each entry one step earlier to hide its latency. It made things slightly worse: the batch-32 call went from 445.5 to 450.7 µs. That negative result was the useful one, because it told me the latency was not in the indices.

The problem was how the warp touched memory. Each pair of lanes copied one token row, so one instruction reached 16 different rows, each needing its own page lookup, and used only half of two 32-byte sectors in each. Every sector ended up requested twice, by two separate instructions (Figure 3). I remapped the lanes so that eight of them copy one aligned 128-byte row together, 16 bytes each: one instruction now covers four complete rows. On the same shape the call fell from 450.7 to 206.3 µs. The same version also loaded each page id once per token and shared it with a warp shuffle, and added an L2 prefetch hint, so I count the gain for the three together.

The final kernel takes 180.1 µs on that shape against FlashAttention-3's 384.3 µs (2.13×), an effective 3.64 TB/s of nominal KV data. The remaining distance to the 136.5 µs floor is the part I understand least. Figure 4 shows all twelve timed shapes: the long-context ones are where the gather work pays, and the short sliding-window ones are a different problem, covered below.

Splitting the context, and merging it back

A single request has only two KV heads, far too little parallelism for 132 SMs, so the context has to be split. I give every block an equal share of all requests' keys laid end to end, which fills one wave whatever the mix of lengths; a block that straddles two requests simply produces two partial results (Figure 5). Each partial keeps a running maximum and normalizer, and a merge kernel combines them with a base-2 log-sum-exp. The split buys parallelism with partial-result traffic and an extra kernel, and at batch one that merge is a visible share of the call.

Verify needed tensor-core math

Verify has a different bottleneck. Eight draft tokens raise the math per cached byte eightfold, to about 128 FLOP per byte, so the gather stops being the whole story. To see what limited my verify kernel I built three variants of it on a synthetic batch-32 full-context case: the full kernel took 424.9 µs, a loads-only version 176.0 µs and a math-only version 395.3 µs (Figure 6). The math alone, including its FP8-to-FP16 conversions, took nearly all of the time and barely overlapped the loads.

So I moved both matrix products to FP8 warpgroup MMA (wgmma), with operands in shared memory and causal masking inside the 8-token block. An earlier layout choice helped here: the gather already writes each row in the 128-byte swizzle that wgmma's shared-memory descriptors expect, so the keys are used exactly where they land.

Getting there took a detour. My first wgmma version kept one operand in registers and failed 13 of 16 tests, with errors near 1.41 on every full-context verify test, as if each MMA were reading the previous one's register operand. Moving both operands to shared memory fixed it. I treat that as a working fix rather than a diagnosis; my own fence ordering or register lifetimes could explain it as well as the hardware.

Decode still uses FP8 mma.sync, and on Hopper that instruction does not run natively in FP8: compiling one for sm_90a yields twelve F2FP conversions and two FP16 HMMA operations (see the appendix). A wgmma decode tile is where I would look for the next attention gain.

Sliding-window layers: one launch per call

Sliding-window layers have the opposite problem. A call moves only 0.5 to 17 MB of KV data, under 4 µs of transfer at 4.8 TB/s, so launches and synchronization decide its time. I gave each request one Hopper thread-block cluster that normalizes and rotates the new token, writes it to the cache, attends over the window on 6 to 16 SMs and merges partial results through distributed shared memory, all in one launch. Batch-one sliding decode takes 7.0 µs this way, against 21.0 µs for the baseline's chain of separate kernels.

One shape stayed slow, and I only understood why after writing SM ids and timestamps from inside the kernel. At verify batch 16, the 112 blocks of 16 clusters of seven ran on 106 SMs, so 12 blocks had to share an SM in pairs. Those blocks spent 17.3–18.6 thousand cycles in their KV loop against a median of 10.7 thousand for blocks alone on an SM, and the whole call waits for its slowest cluster (Figure 7). Moving that shape to clusters of six, with shared memory padded so that only one block fits per SM, brought it from 18.1–18.3 µs to 15.1–15.6 µs over two runs each.

Open questions
  • Whether the remap cut memory traffic or only request count: an L2 and DRAM sector comparison of the two versions would tell.
  • The remap on its own, without the page-id and prefetch changes.
  • Where the rest of the distance to the floor goes at batch 32: bytes in flight per SM and the FP16 conversion of V are my suspects.
Correctness

A stale read under programmatic dependent launch

The bug I learned the most from passed every unit test. For verify at batch one on sliding-window layers, a small prologue kernel normalizes and rotates the eight new query rows, writes them in FP8 to a buffer q8, and immediately tells its dependents they may launch. Under PDL the attention kernel starts early, works out its partition and issues page-table loads, then executes griddepcontrol.wait. Only after that wait may it read q8, because the wait is what guarantees the prologue's writes are visible.

The judge's timed recheck, which replays the graph on fresh inputs, failed on that one shape with a relative error of 0.777 against an allowed 0.15, as if the kernel had read the previous call's queries. The PTX showed why: the q8 loads had become non-coherent, read-only loads (ld.global.nc) and had moved above the wait (Figure 8). I had declared q8 as const __restrict__, which promises the compiler that nothing changes the buffer while the kernel runs. A PDL producer running concurrently breaks that promise, so moving the loads was legal, and the wait's own "memory" clobber did not stop it.

This bug also depends on the compiler. A later rebuild of the same source with nvcc 13.5 happened to keep the loads below the wait, still on the read-only path:

griddepcontrol.wait;
  ...
ld.global.nc.u32    %r494, [%rd74];        // q8 loads, read-only path, now below the wait
ld.global.nc.u32    %r495, [%rd74+16];

The declaration is wrong either way. The fix reads q8 after the wait with an ordered ld.global.cg in volatile inline assembly with its own memory clobber, so the compiler keeps the two in program order; it passed every recheck.

__device__ void pdl_wait() { asm volatile("griddepcontrol.wait;" ::: "memory"); }

// before: q8 is const uint8_t* __restrict__, and this load became ld.global.nc above the wait
qa = *reinterpret_cast<const uint32_t*>(q8 + off);
// after: read q8 once the wait has returned, with an ordered L2 load
asm volatile("ld.global.cg.u32 %0, [%1];" : "=r"(v) : "l"(p) : "memory");

Correctness had a price: the ordered loads cost 4.1 µs on batch-one full decode and 7.0 µs at batch 16, so I enabled PDL only where the prologue sits on the critical path, verify at batch one on sliding layers. My rule since then is simple: never read a PDL producer's output through the read-only path. The experiment that would pin the explanation down, removing only __restrict__, I have not run.

Mixture of experts · score 1.94× over Marlin

Keeping expert weights in registers

Each GPU holds 32 of the 256 experts. One expert is 3 × 4,096² weights in NVFP4: 4-bit E2M1 codes (0, ±0.5, ±1, ±1.5, ±2, ±3, ±4, ±6) with one E4M3 scale per 16 weights, 28.31 MB before the FP32 global scales of the gate/up and down tensors. Activations are BF16, so every weight has to become BF16 before it reaches the tensor cores. In decode each expert serves only a few tokens, so the experts the router touches set the minimum weight traffic, and the job is to stream those bytes as fast as HBM allows.

Marlin, the baseline, moves these weights at an estimated 0.90–2.17 TB/s, 19–45% of the peak. Early on I measured how fast a plain loader could stream the packed weights: 3.90–4.05 TB/s for 604 MB with a cp.async ring. My GEMM at the time managed about 2 TB/s, so memory was not the limit; the instructions spent on dequantization and the round trip through shared memory were, and a count of the compiled instructions agreed. That told me where to look: make dequantization cheap, and keep the weights out of shared memory.

The bit placement in Figure 9 is what makes the kernel cheap. There is no lookup table and no float conversion: the code's bits are already a tiny BF16 number once they sit in the right place, and the block-scale multiply that has to happen anyway also undoes the 2−126. The final kernel then puts 16 weight rows on the 16-row side of mma.sync m16n8k16 and up to 8 tokens on the 8-column side. With one token, seven of the eight columns multiply zeros. I accepted that waste on purpose: the time was going into dequantization and data movement, and in exchange the dequantized weights feed the MMA straight from registers. From 8 to 256 tokens each lane loads its weights with ld.global.nc.L1::no_allocate into a 4- to 8-stage register window that never touches shared memory; at a single token, a shared-memory ring turned out to be faster.

The register path wins while each weight serves only a few tokens. At 32 tokens my kernel's lead narrows to 1.45× (143.6 against Marlin's 207.7 µs), because the same warps must issue both the loads and the math. By 128 and 256 tokens the busiest expert receives an estimated 63 and 140 tokens and would be dequantized over and over, so experts with more than 32 tokens go to a second kernel that feeds each dequantized fragment to eight MMAs instead of one or two. That kernel launches right behind the main persistent kernel without waiting at its start, fills SMs as the main kernel's blocks retire, and waits only at its end. I suspect a design that stages weights through shared memory would win once reuse gets high enough, and I would like to know where that crossover sits.

Prefill needed a different layout

Prefill reverses the balance. At 753 to 16,384 new tokens the busiest experts receive hundreds or thousands of tokens each, so every weight is reused many times and the math dominates. Activations must stay in BF16, which rules out the FP8 tensor cores. None of the libraries I checked during the challenge (CUTLASS examples 55 and 69, FlashInfer, TensorRT-LLM and triton_kernels) offered an NVFP4 grouped GEMM with 16-element scale groups for Hopper, so I wrote one in Gluon, Triton's lower-level dialect.

I started in plain Triton 3.8, which compiled the dequantization loop to about 7.6 SASS instructions per weight, and I found no way to give it the register layout it needed. Gluon's explicit layouts let each thread load whole 32-bit words that decode straight into its own fragment, and the dequantized weights feed wgmma as its register operand. That is the arrangement that failed me in the verify kernel, so I checked it hard: here the compiler emits the wgmma sequence, and the Gluon kernel matched my earlier Triton kernel bit for bit in a self-test on the judge and passed every judge test.

On the 753-token expert GEMMs the Gluon kernel took 474 µs against 717 µs for my earlier Triton kernel, which itself ran level with Marlin at 707 µs. That looked like a solid win until I logged the judge's actual routing. My tuning had spread tokens evenly over the experts. The real routing looks nothing like that (Figure 12).

One expert receiving almost every token changes what a good kernel looks like. A grid sized for the worst case was mostly empty tiles, each holding an SM, so I made the kernel persistent over active tiles only: 511.0 µs instead of 550.7 µs with the judge's routing. In a later run, a small-tile region for the long tail of lightly used experts took it from 510.8 to 455.7 µs. At 16K tokens I went further and expanded the eight busiest experts from 4-bit to BF16 on every call, running them through DeepGEMM's BF16 grouped GEMM while the rest stayed on my kernel; the expert layer took 4,711 µs against 5,203 µs with the 4-bit kernel alone. That last result comes from tuning on one H200 and never ran in the server.

The prefill layer as a whole

The scored prefill layer wraps this expert path with cuBLAS for the dense projections and FlashAttention-3 for attention, plus routing-layout and combine kernels I rewrote around the expert GEMM. I deliberately left the dense GEMMs to the library: at these sizes it is already near the best algorithm I could find. Per shape, the layer is 1.29× faster on the first full-attention turn and up to 1.75× on a 16K-token first turn over a cached sliding window (Figure 13).

Open questions
  • Tensor-core utilization in the decode kernel, to confirm the zero-padded columns really are free.
  • Where a shared-memory design overtakes the register path: a sweep over tokens per expert on real routing would find it.
  • Whether the 16K hot tier holds up inside the server.
SGLang v0.5.23 · 8×H200

What carried over to eight GPUs

The last stage moved the work into SGLang, serving the full model on eight H200s to 1, 4, 16 and 32 concurrent users of multi-turn coding conversations, with DFlash speculative decoding: a small drafter proposes 8 tokens, the full model checks them in one pass, and each step committed 3.9 to 4.2 tokens on average. The challenge scores throughput per GPU at the per-user output speed the stock server reaches, and caps time to first token at twice the stock server's, so there is no trading user latency for throughput.

I expected the kernels to carry over directly. They did not, and the reason is what this workload spends its time on. The benchmark counts cached prompt tokens as throughput: at one user it credits the node with 52,705 tokens per second while the user receives 142 output tokens per second. Each conversation opens with a 74,160-token prompt, and as users are added, those first prompts take over the GPUs. I built a simple time model from the per-kernel times; it reproduced the stock server at all four loads and predicted two of my gains closely, and it says first-turn prefill takes half to almost three quarters of GPU time (Figure 14).

That picture explains the rest of this section. Decode kernels, the ones I had worked hardest on, are a shrinking share as load grows; anything that frees GPU time during the long first prompts matters more. Figure 15 builds the server up one change at a time.

The one change the challenge scored has nothing to do with my kernels: it reshapes the KV-cache budget. Muse Spark has 46 sliding-window layers and 16 full-attention layers, yet SGLang's generic default gives the sliding-window pool 0.8 of the budget, as though it needed the whole context. A Muse-specific default of 0.1 moves that memory to the full-attention pool, which grows from 1,889,034 to 3,854,370 token slots. The change scored 1.022× across the four loads, with almost all of the gain at 32 users: 1.065×, or 12,638 to 13,454 tok/s/GPU. That is the load where long prompts fill the full-attention cache fastest, which is consistent with capacity limiting the stock server there.

The kernels added more on top in shorter tests. With the MoE kernel on top of the KV pool, the server reached 1.200× at one user (6,282 to 7,541 tok/s/GPU) and 1.229× at 32 (12,638 to 15,533); with the prefill row split instead, 1.136× at 32 (12,695 to 14,418). With all four changes stacked, a 16-user test reached 1.283×: throughput rose from 12,301 to 15,781 tok/s/GPU while each user's output rate rose from 17.2 to 22.2 tok/s, outputs agreed with stock, and peak memory stayed within 0.1 GB of it. First-token latency improved alongside throughput (Figure 16).

Reading the shorter tests
  • They describe combinations and do not isolate any single change. The scored KV-pool run gave 1.003× at 16 users against a different stock measurement, so the two cannot be subtracted.
  • The stacked run reports 1.283× as its scoring statistic and also lists a same-load throughput ratio of 1.30, which I could not reconcile without the benchmark's internals.
  • The stacked server had fewer full-attention slots, 2,389,448, than the MoE-only runs (2,516,076) or the KV-pool change alone (3,854,370); which change took the memory is still open.

One experiment went the other way, and I think it is the most instructive. I tried scheduler settings that hold prefill back behind running decodes. They scored 0.990×. At 16 users the later-turn 90th percentile time to first token reached 1.49 s against stock's 0.34 s, over the cap, so that load was excluded and counted at 0.964 (11,766 against 12,208 tok/s/GPU). The other three loads stayed within 1% of stock. In hindsight Figure 14 predicts this: on this workload prefill is most of the work, and delaying it only moves the queue.

Limits

What carries over, and where it stops

The three questions from the opening decided every design here: bytes moved, reuse per byte and the gating dependency. The answers, though, depend on page size 1, the FP8 cache, the judge's routing and Hopper itself. On another GPU the lane mapping, fragment layout, wgmma placement, cluster sizes and PDL behavior would each need fresh work, and the layer result rests on one shape on one H200, without collectives and without a trace.

The serving result is the one I would weigh most carefully. The scored gain came from how SGLang divides its KV memory, and the kernels' gains showed up only in shorter tests of combined changes. A full four-load run of all the changes against a fresh stock baseline is the experiment I most want to see.

What I would build next

  • A persistent decoder-layer kernel that keeps the whole batch-one layer on chip, to remove the dozen kernel boundaries that Figure 2 is about.
  • A wgmma decode tile for attention, to stop paying for FP8-to-FP16 conversion on every MMA.
  • A prefill-first server: the time model says first prompts own the GPUs at high load, so that is where the next serving gain should come from.
Appendix

Methods and implementation notes

How the kernels were timed

Each kernel workload ran in the judge on one H200 SXM against its SGLang baseline, with PyTorch 2.14.1 and CUDA 13.0.3; the judge does not publish the driver, clocks or power policy. A timed call is a CUDA-graph replay of one invocation on fresh inputs, preceded by reading a buffer larger than the 50 MB L2. My replays and SGLang's take turns on the same inputs in swapped pairs, and the judge subtracts its fixed replay cost of about 4 µs from both sides. A shape's speedup is the median over repetitions (60 for the decode layer) of SGLang's time divided by mine, and my per-shape time is SGLang's median divided by that speedup.

A workload's score combines shapes into loads. A load's time is the weighted sum of its shapes' times, and the score is the geometric mean over loads of SGLang's load time divided by mine:

WorkloadLoadsHow shapes are weighted
Attention, decode layer6Each load pairs a sliding-window shape (weight 46) with a full-attention shape (weight 16), matching the layer counts
Prefill layer3Turn loads plus a first-turn load with weights 16, 138, 16 and 16
Projections6Five layers per load
MoE6One shape per load

Recomputing from the per-shape times reproduces the judge's 1.968 and 1.733. Because loads mix shapes, a single shape can land outside a workload's load range: the batch-one layer in the opening (2.07×) is half of the batch-one decode load, which scored 2.04×. Each run reports a 95% interval of at least ±1.5%; the judge does not say how it is formed, and it reflects timing noise on one input stream rather than variety in the inputs. My own tuning used the same replay and read-flush method, after an early write-based flush left dirty lines whose write-back inflated every timing by 6–11 µs and led the tuner to pick the wrong configurations.

All the final kernels passed every judge test under the challenge's precision rules: expert weights stay in NVFP4, dense weights in BF16 and the cache in FP8; attention may use FP8 queries and softmax probabilities; the FP32 router may run as a BF16 high/low pair with FP32 accumulation; and every key in the window or context is attended. Projection outputs must be within 1% relative L2 error of an FP64 reference, and the router's within 0.01%. On the server, each run compared its outputs with the stock server by KL divergence and prefix agreement over 32 reference turns, and every run reported here passed.

Projections: fewer bytes, and a one-launch router

At one token a projection is a pure weight stream. The pooler (4,096 × 8,192, BF16) is 67.1 MB, a 13.98 µs floor at 4.8 TB/s. A 12-bit encoding keeps each weight's low byte and replaces its high byte with a 4-bit code, the sign plus an offset into a 16-binade window ([2−19, 2−3) for these matrices), which shrinks the payload to 50.3 MB and the floor to 10.49 µs before correction data.

Weights inside the window reconstruct bit-exactly; the few outside it, about 1.4 per 10,000, are stored as a fixed value plus an exact FP32 correction applied after the GEMM, whose exact size I did not count. My kernel runs the batch-one pooler in 14.93 µs against cuBLAS's 20.75 µs (1.39×). At larger token counts it picks, per shape and at load time, among cuBLAS, cuBLASLt algorithms and my own kernels, so part of the projection score there comes from choosing the best library algorithm. Its one-hot probe rows, which read single weight columns, come out exact.

The router scores 256 experts per token with FP32 weights, because a small error can change which experts are picked. My kernel splits each weight into two BF16 halves, w ≈ hi + lo (about 16 significant bits), and runs both tensor-core products into one FP32 accumulator in a single launch; the baseline runs an FP32 GEMM at up to 8 tokens and two BF16 GEMMs with separate reductions above that. The relative L2 error against the judge's FP64 reference was 2.6×10−6 on its 8- and 9-token tests, against a limit of 10−4 and 2.9×10−6 for the stock router. I checked the score error and the judge's selection rule, under which each chosen expert must score within 0.05 of the reference's eighth best, but not top-8 agreement on near-tie rows.

Attention implementation notes

Cluster size is chosen per shape with cudaOccupancyMaxActiveClusters, and shapes or devices without the larger cluster sizes fall back to the split kernel. The scheduling trace recorded SM ids and %globaltimer per block and phase. At batch 32 the 224 blocks cannot avoid sharing at clusters of seven, and clusters of 4 lost because each block then reads more of the keys.
